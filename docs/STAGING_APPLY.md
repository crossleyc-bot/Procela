# Staging apply — stand the stack up in a throwaway account

A condensed, ordered runbook for bringing Procela up in a **staging** AWS
account end-to-end: infra → secrets → schema → first admin → deploy pipeline →
smoke test. It stitches the reference guides together in the order you actually
run them; follow the links for detail.

> The Terraform module has been `terraform validate`d clean against the AWS
> provider (v5). It has **not** been `apply`d — a real apply needs your AWS
> account + credentials, which is what this guide walks you through.

## 0. Prerequisites

- An AWS account for staging (ideally isolated — several hardening toggles
  default on, e.g. Multi-AZ RDS, WAF; you can turn the cost-bearing ones off,
  see step 2).
- `terraform` ≥ 1.6, `aws` CLI configured for the staging account, `gh` CLI
  (for the deploy-pipeline variables), Docker (for the first image push).
- Two ACM certs: one in `var.region` for the ALB, one in **us-east-1** for
  CloudFront (`docs/STATUS.md` § Production hardening; `deploy/terraform/README.md`).

## 1. Remote state (recommended even for staging)

Create the S3 bucket + DynamoDB lock table, then uncomment the `backend "s3"`
block in `versions.tf` and `terraform init`. See `deploy/terraform/README.md`.

## 2. Apply the infrastructure

```bash
cd deploy/terraform
cp terraform.tfvars.example terraform.tfvars   # then edit:
#   environment = "staging"
#   alb_certificate_arn / cloudfront_certificate_arn / domain_name
#   app_image  = "<ecr_repository_url>:bootstrap"  (any tag; see step 5)
#   enable_cicd_deploy_role = true ; github_repo = "datalign-technology/procela"
#   For a cheaper staging box, paste the "cheap dev stack" override block.
terraform init
terraform plan      # review — several toggles create real, billable resources
terraform apply
```

The ECS service is created now but its tasks can't pull until the first image
exists (step 5) — that's expected.

## 3. Populate secrets

`ANTHROPIC_API_KEY`, the RS256 JWT keypair, and (if enabled) SMTP/OIDC secrets
go into Secrets Manager. DB password, `DATABASE_URL`, JWT HMAC fallback, MFA
key, SCIM token, and the Redis URL are **generated by Terraform**. Full catalog
+ `put-secret-value` commands: `docs/DEPLOY_RUNBOOK.md` §1–3.

## 4. Apply the database schema

```bash
terraform output -raw migrate_run_task_command | bash   # in-VPC Fargate task
```

## 5. Wire the deploy pipeline + first deploy

```bash
# Set the GitHub repo variables from the outputs (one-liner in the
# deploy.yml header), then run the pipeline to build + push the first image
# and roll the service:
gh workflow run deploy.yml
```

After this the ECS service is running the real image. Details + the var⇄output
map: `.github/workflows/deploy.yml` header and `DEPLOY_RUNBOOK.md` §3a.

## 6. Bootstrap the first admin + IdP

Set `BOOTSTRAP_SUPER_ADMIN_EMAIL` / `BOOTSTRAP_ORG_NAME` and point the app at
the customer's (or a test) IdP, then log in. Full flow, including SSO
domain→org routing: `docs/CUSTOMER_ONBOARDING.md`.

## 7. Smoke test

- [ ] ALB target group **healthy** (checks `/api/v1/health`).
- [ ] CloudFront serves the frontend; `/api/*` reaches the backend.
- [ ] Bootstrap admin logs in via the IdP as `SUPER_ADMIN`.
- [ ] `GET /api/v1/health/config` shows `aiConfigured: true`.
- [ ] A trivial deploy (push to the default branch) rolls through the pipeline.

## Tear down

`terraform destroy`. Note: `rds_deletion_protection` defaults **on**, so set it
`false` (and re-apply) before destroying a staging DB, or the destroy is blocked.

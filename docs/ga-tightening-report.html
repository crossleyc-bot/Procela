Procela · v1 readiness review

Does every field earn its place?

We inspected every piece of information Procela stores — about 653 fields across 63 areas of the product — to get the first paid release tight, stable, and easy to run. Here's what we found, in plain terms.

The good news first

This is a tightening job, not a rebuild. The parts that carry the product are solid and fully wired: login & security (SSO, multi-factor, single sign-on directory sync), the process catalog, the governance suite, and the real data connectors (the on-prem agent and dbt).

Roughly nine in ten fields are doing real work. The findings below are the remaining tenth — the cruft, duplication, and half-finished edges that make a v1 feel loose instead of tight.

What needs attention · fields

Four things keeping the data model from being tight

Remove8 fields

Dead weight

Left over from earlier versions of the design. The application never reads or writes them — they just sit in the database adding noise and inviting confusion. Safe to delete.

System.stewardIdreplaced long ago by a proper multi-owner list
DataAsset.rejectedSensitivityTagsa leftover companion to a field that is used
Person.departmentorphaned when storage moved to the database
Do: drop the columns in one reviewed change — pure subtraction, no behaviour changes.
Merge~5 fields

Two fields for the same idea

The same concept is stored two different ways, so screens and reports can quietly disagree about which one is "true."

Person.role vs orgRolesan old single-role field beside its per-team replacement
Person.title vs jobRoletwo overlapping job-description fields
System.integrationPoints vs integrationsfree text beside the structured version that supersedes it
Do: keep one of each pair and migrate the content over.
Decide~12 fields

Looks like a feature, but isn't

These are the trap for a commercial release: fields a user can fill in that have no effect. They mislead people into thinking something is configured when nothing happens.

Agent.skillIdsyou can pick an AI agent's "skills," but the engine ignores them
RaciOverride.reasona reason box that always saves the same fixed words
GlossaryTerm.relatedTermsstored, but no screen ever shows it
Do: for each — either make it actually work, or remove it. Nothing on screen should be decorative.
Resolvedreal vs. simulated

"Connect your data" is now real for all but two source types

Direct database, cloud-warehouse (Snowflake / BigQuery / Databricks / Redshift), MongoDB, and cloud object-storage (S3 / Azure Blob / GCS / SFTP) discovery all connect for real; only API and spreadsheet sources still return clearly-labelled sample data (shown behind a "simulated" banner so nothing pretends to be live). The two saved secrets (a dbt token and an SSO client secret) were moved into the existing encryption layer.

Done: real drivers shipped across databases, warehouses, MongoDB, and object storage; API/spreadsheet remain honestly labelled as sample; both secrets are now encrypted at rest.
What needs attention · running it

Three things that decide "stable and easy to manage"

Stability

Background jobs can run twice

If you run more than one copy of the server for reliability — the normal way to stay online — today each copy independently runs every scheduled job: AI agent runs, email digests, data-quality checks. That means doubled AI costs and duplicate notifications to users.

Do: add a simple "one server owns the schedule" switch so jobs fire once.
Permissions

Read-only users can still make edits

The six roles (Admin, Process Owner, Data Steward, Viewer, and so on) exist, but on most screens the app doesn't actually check them before saving a change. A "Viewer" can currently edit the catalog.

Do: enforce the roles on every create/edit/delete, not just the admin screens.
Correctness

Two real bugs, found along the way

A mismatched field name silently switches off one governance signal, and an AI-schedule save can skip the database — so a schedule may forget when it last ran and repeat itself after a restart.

Do: both are small, contained fixes.
Recommendation

What we'd do, in order

  1. no data changes

    Make it stable

    Jobs run once, roles enforced on edits, the two bugs fixed. This protects a real, always-on deployment first.

  2. one migration

    Remove the 8 dead fields

    Pure clean-up — delete what nothing uses. No behaviour changes.

  3. one migration

    Merge the duplicates

    Collapse each "two fields, one idea" pair down to a single source of truth.

  4. product calls

    Decide the "phantom" fields

    Go through the ~12 do-nothing fields one by one: wire it up, or take it out.

  5. before launch

    Finish or hide the simulated bits

    Ship only real features, and encrypt the two plain-text secrets.

Plus light polish: make owner-field names consistent across the product, and document the handful of settings that aren't yet written down.

How we checked

For every field we traced whether the app actually reads or writes it, and whether any screen ever shows it. A field that's stored but never touched on either side is "dead." Six reviewers each took a section of the product in parallel. The full field-by-field detail, with evidence and the staged migration plan, lives in docs/GA_TIGHTENING_AUDIT.md.
